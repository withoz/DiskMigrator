# DiskMigrator-X — Claude 연계 계획

> **제품명: DiskMigrator-X.** 기존 수동 버전(DiskMigrator v1.x)과 구분되는, 완전히 새로운 앱입니다.
> 이 문서는 `mcp` 브랜치의 계획서이며 `master`(v1.4.1)는 손대지 않습니다 —
> 지금까지의 수동 버전은 그대로 쓸 수 있어야 합니다.
>
> **작업 폴더**: `D:\aimigration-x` (git worktree, `mcp` 브랜치 고정).
> `D:\aimigration`은 `master`(v1.4.1)로 남습니다. 저장소는 하나이므로 Core/Windows를 공유하고,
> 진단 엔진을 수동 버전으로 역이식하기도 쉽습니다.

## 1. 무엇을 만들려는가

사용자가 하고 싶은 말을 그대로 하면, Claude가 **디스크 상태를 직접 읽어 정확히 진단하고**,
**안전한 계획을 세워 설명하고**, **사용자 확인 아래 실행하고**, **부팅까지 확인·복구**하는 흐름.

제품 철학인 *"디스크만 고르면 되는 자동 판단"* 을 대화로 확장하는 것이며,
없던 기능을 만드는 게 아니라 **이미 검증된 엔진을 Claude가 쓸 수 있게 여는 일**입니다.

### 이 계획의 출발점 — 2026-08-04 부팅 조사

며칠에 걸친 조사에서 진단 스크립트를 열 개 넘게 그때그때 만들었습니다.
전부 읽기 전용이었고, 도구로 있었다면 작업이 훨씬 짧았을 것입니다.
**1단계는 그 경험을 그대로 옮기는 일입니다.**

## 2. 사용 시나리오 — 이것이 되면 성공이다

도구 목록보다 시나리오가 먼저입니다. **각 시나리오를 끝까지 수행할 수 있어야** 그 단계가 끝난 것입니다.

### S1. 새 SSD로 이사 (1~3단계 전부)

> **사용자**: 새 1TB SSD를 샀어. 지금 윈도우를 그대로 옮기고 싶어.

Claude가 하는 일:
1. `list_disks` → 원본(시스템 디스크 0, 931GB 사용 중 420GB)과 후보 대상 식별
2. `inspect_disk` → 대상이 비어 있는지, 파티션 배치가 어떤지
3. `evaluate_safety` → **차단·경고 사유 전부**를 근거로 설명
   *"대상이 원본보다 작지만 사용량이 420GB라 축소로 가능합니다. 대상의 기존 데이터는 전부 지워집니다."*
4. `plan_clone` → 무엇이 어디로 가는지, 예상 시간
5. `propose_clone` → **앱 화면에 확인 카드**. 사용자가 모델명 확인 후 실행
6. 진행 중 `get_progress`로 상황 설명
7. 완료 후 `check_boot_readiness` → 문제 있으면 `propose_boot_repair`

### S2. "복원했는데 부팅이 안 돼요" (1~2단계)

> **사용자**: 백업을 복원했는데 로고에서 멈춰. 뭐가 문제야?

이번 부팅 조사를 그대로 재현하는 시나리오입니다.
1. `check_boot_readiness` → BCD 장치 참조·저장소 드라이버·재개 이미지
2. `read_boot_drivers` → Start=0 드라이버 전수 + **파일 존재 확인**
3. `read_fast_startup` → `hiberfil.sys`·`HiberbootEnabled`
4. `audit_esp` → 부팅 파일·BCD·**서명 인증서(2011 PCA vs 2023 PCA)**
5. `analyze_boot_trace` → **커널이 어디까지 갔는지**(파일 타임스탬프)
6. `explain_boot_failure` → 위를 엮어 원인과 다음 조치

> 실제로 이번 조사에서 결정적이었던 것은 *"`bootstat.dat`만 갱신되고 하이브·이벤트로그는 그대로"* 라는
> 한 줄이었습니다. 그 판단을 도구가 해 줍니다.

### S3. 백업 파일이 멀쩡한지 확인 (1단계)

> **사용자**: 작년에 받아둔 백업인데 쓸 수 있을까?

`inspect_image` → VHDX 구조·파티션 테이블·볼륨별 chkdsk. 손상되었으면 **복원 전에** 알려줍니다.

### S4. 정기 백업 조언 (1~3단계)

> **사용자**: 지난번 백업 이후로 뭐가 바뀌었지? 증분으로 받을 수 있어?

`inspect_image`로 사슬(base→-01→-02)을 읽고, `propose_backup`으로 증분 백업을 제안합니다.

## 2.5 부팅 불가 PC를 어떻게 볼 것인가 ★

**가장 중요한 상황이자 가장 어려운 상황입니다.** 부팅되는 PC는 급하지 않습니다.

문제는 단순합니다: **PE에는 Claude가 없습니다.** WinPE는 램디스크 최소 환경이라
Claude Code를 돌릴 수 없고, 네트워크도 보장되지 않습니다.

그런데 2026-08-04 조사에서 우리가 실제로 한 방식이 답의 절반이었습니다 —
**디스크를 정상 PC로 가져와서 분석했습니다.** 이걸 제품화합니다.

### 두 가지 경로

```
                    부팅이 안 되는 PC
                           │
         ┌─────────────────┴─────────────────┐
         │                                   │
   [경로 A] 디스크를 뽑을 수 있다      [경로 B] 뽑을 수 없다
   (SATA·USB 어댑터·외장 케이스)      (노트북 납땜·M.2 접근 곤란)
         │                                   │
   정상 PC에 연결                     PE USB로 부팅
   Claude가 직접 진단                  앱이 진단 파일 저장 → USB
   (오늘 한 방식, 실시간)              파일을 정상 PC로 옮김
         │                             Claude가 파일을 읽고 분석
         │                                   │
         └─────────────┬─────────────────────┘
                       ↓
              원인 규명 → 조치 안내
              (조치는 해당 PC에서 수행)
```

### 경로 A — 디스크를 가져온다 (실시간)

오늘 한 그대로입니다. 문제 디스크를 정상 PC에 연결하면 **1단계 진단 도구가 전부 그대로 동작**합니다.
`deviceNumber`만 다를 뿐입니다.

**필요한 추가 설계**
- 진단 도구는 **시스템 디스크가 아닌 디스크**도 당연히 다뤄야 한다(이미 그렇게 설계됨)
- 오프라인 디스크 자동 처리 — 온라인 전환·임시 문자 부여·작업 후 원복.
  오늘 스크립트마다 반복했던 것을 도구가 알아서 한다
- **읽기 전용 보장** — 남의 PC 디스크다. 실수로 쓰면 안 된다

### 경로 B — 진단 파일을 옮긴다 (오프라인 브리지) ★ 핵심

**PE에서 앱이 모든 진단을 수행해 파일 하나로 저장하고, 그 파일을 Claude가 읽습니다.**

이 방식의 가치:
- **PE에 아무것도 필요 없다** — 네트워크·Claude·인터넷 전부 불필요
- **한 번에 다 담는다** — 오늘처럼 "이것도 확인해주세요"를 열 번 왕복하지 않는다
- **나중에 비교할 수 있다** — 조치 전후 두 파일을 diff (오늘 `bootsnap-before/after`가 정확히 이것)
- **Claude 없이도 쓸모 있다** — 포럼에 올리거나 우리에게 보낼 수 있는 표준 진단 리포트

#### 무엇을 담는가 — 2026-08-04 조사에서 실제로 필요했던 전부

| 구획 | 내용 | 왜 필요했나 |
|---|---|---|
| `system` | 수집 시각·앱 버전·PE 여부·수집 PC 정보 | 언제 어디서 찍은 것인지 |
| `disks[]` | 디스크·파티션 배치(오프셋·크기·타입·FS·레이블·사용량)·GPT GUID·MBR 서명 | 구조 파악의 출발점 |
| `esp` | 파일 트리·**BCD 전체 덤프**·부팅 관리자 **서명 발급자**(2011 PCA vs 2023 PCA) | 부팅 파일 완전성. 서명은 구형 보드 호환성 판정에 결정적 |
| `hive.bootDrivers[]` | Start=0 드라이버 **전수** + **파일 존재 여부** + 표준 위치 밖 표시 | 파일 하나만 없어도 커널이 멈춘다 |
| `hive.fastStartup` | `HiberbootEnabled`·`HibernateEnabled`·`hiberfil.sys` 유무/크기 | 다른 하드웨어에서 재개 실패 → 로고 정지 |
| `hive.pnpStorage[]` | `Enum\PCI`의 저장소 컨트롤러 항목(하드웨어 ID → Service) | NVMe/AHCI 인식 준비 여부 |
| `hive.select` | Current·Failed·LastKnownGood | 부팅 실패 이력 |
| `bootTrace` | `bootstat.dat`·SYSTEM·SOFTWARE·evtx·setupapi·CBS·`ntbtlog` **타임스탬프** | **커널이 어디까지 갔는지** — 이번 조사의 결정적 단서 |
| `ntbtlog` | 있으면 마지막 N줄 + `NOT_LOADED` 항목 | 어느 드라이버에서 멈췄나 |
| `setupapi` | 최근 장치 설치 기록(특히 저장소·칩셋) | 어느 PC에서 부팅했었는지, 무엇이 설치됐는지 |
| `volumes` | dirty 여부·chkdsk 요약 | 파일시스템 손상 여부 |
| `verdict` | 앱이 스스로 내린 1차 판정(`BootReadinessCheck` 결과) | Claude 없이도 답이 나오는 경우가 많다 |

> 이 목록은 추측이 아니라 **이번 조사에서 실제로 필요했던 것**입니다.
> 특히 `bootTrace`의 타임스탬프 비교는 *"`bootstat.dat`만 갱신되고 하이브·이벤트로그는 그대로"* 라는
> 결정적 판단의 근거였습니다.

#### 형식과 제약

| 항목 | 설계 |
|---|---|
| 형식 | **JSON**(기계 판독) + 같은 내용의 **요약 텍스트**(사람이 바로 읽음) 한 파일에 |
| 확장자 | `.dmdiag`(실체는 JSON) — 더블클릭 오동작 방지 |
| 크기 | **목표 1MB 이하.** `ntbtlog`·`setupapi`는 전문이 아니라 관련 부분만 발췌 |
| 민감정보 | 시리얼·볼륨 레이블 **기본 마스킹**, 저장 시 "상세 포함" 선택 가능 |
| 무결성 | 해시 포함 — 옮기는 중 깨졌는지 확인 |
| 쓰기 없음 | **수집은 순수 읽기.** 대상 디스크에 아무것도 쓰지 않는다(하이브도 읽기 전용으로 연다) |
| 저장 위치 | PE에서는 USB(앱이 실행 중인 매체) 기본. 대상 디스크에 저장하지 않는다 |

#### UI — PE에서도 초보자가 할 수 있어야 한다

부팅 복구 탭에 버튼 하나를 더합니다:

> **[ 진단 리포트 저장 ]**
> 이 디스크의 부팅 관련 정보를 파일 하나로 모읍니다. 디스크는 수정하지 않습니다.
> 저장한 파일을 다른 PC로 옮겨 도움을 받을 수 있습니다.

누르면 대상 선택 → 수집(진행률) → 저장 위치 선택 → 완료 화면에
**"파일을 USB에 저장했습니다. 다른 PC에서 이 파일을 Claude에게 보여주세요"** 안내.

#### Claude 쪽 도구

| 도구 | 입력 | 출력 |
|---|---|---|
| `load_diagnostic` | `path` | 리포트 파싱 결과 요약 + 앱의 1차 판정 |
| `explain_boot_failure_from_report` | `path` | 원인 후보 + 우선순위 조치(§6.2의 오프라인 버전) |
| `diff_diagnostics` | `pathA`, `pathB` | 조치 전후 비교 — **무엇이 바뀌었나** |

> `diff_diagnostics`는 오늘 `bootsnap-before`/`after` 비교가 **디스크는 아무것도 안 바뀌었다**는
> 결정적 사실을 알려준 것과 같습니다. 그 판단이 "원인은 디스크 밖에 있다"로 이어졌습니다.

### 시나리오 S5 — 부팅 불가 PC 구조 (경로 B)

> **사용자**: 컴퓨터가 안 켜져. USB로 부팅해서 뭘 어떻게 해야 해?

1. Claude가 **부팅 USB 만드는 법**부터 안내(이미 있는 기능)
2. 사용자가 PE로 부팅 → 앱의 **[진단 리포트 저장]** 실행 → USB에 `.dmdiag`
3. 정상 PC로 옮겨 Claude에게: `load_diagnostic`
4. Claude가 원인 후보를 우선순위로 설명 — *"`stornvme.sys` 파일이 없습니다. 이게 직접 원인입니다"*
5. 조치를 안내 → 사용자가 PE에서 수행(부팅 복구·복원 등)
6. 조치 후 **다시 리포트 저장** → `diff_diagnostics`로 실제로 바뀌었는지 확인

**6번이 중요합니다.** 오늘 조사에서 "복구했는데 원래대로"를 여러 번 겪었습니다.
바뀌었는지 확인할 방법이 있어야 합니다.

### 왜 이게 최선인가

- **PE에 Claude를 넣으려는 시도는 실패한다** — 램디스크 용량·네트워크·인증 전부 문제
- **원격 접속은 위험하고 복잡하다** — 부팅 안 되는 PC에 네트워크가 있을 거라는 보장도 없다
- **파일 하나를 옮기는 것은 누구나 할 수 있다** — USB가 이미 손에 있다
- **오늘 실제로 이 방식이 통했다** — 디스크를 가져와 분석했고, 스냅샷 비교로 결론을 냈다

## 2.6 하드웨어 호환성 판정 — "이 조합이 되는가" ★

**이번 조사가 며칠 걸린 이유가 이것입니다.** *"ASRock B360M Pro4에 Crucial P3를 달면 되는가"* 를
미리 알 수 있었다면, 혹은 실패 후 빠르게 판정할 수 있었다면 몇 시간이면 끝났을 일입니다.

목표는 **근거를 들어 정직하게 말하는 것**입니다:
*"이 메인보드로는 이 SSD에서 부팅할 수 없습니다. SATA SSD를 쓰시거나 메인보드를 바꾸셔야 합니다."*

### 수집 가능한 신호 (실측 확인 완료)

| 신호 | 출처 | 판정에서의 역할 |
|---|---|---|
| 메인보드 제조사·모델 | `Win32_BaseBoard` | 알려진 문제 조회의 키 |
| BIOS 버전·**릴리스 날짜** | `Win32_BIOS` | **세대 판정의 1차 근거** |
| SMBIOS 버전 | `Win32_BIOS` | 펌웨어 세대 보조 근거 |
| 펌웨어 유형 (UEFI/Legacy) | `$env:firmware_type`, `SetupAPI` | **Legacy 전용이면 NVMe 부팅 불가 — 확정 판정** |
| Secure Boot 상태 | `SecureBoot\State` (관리자 필요) | 서명 검증 실패 원인 판별 |
| CSM 활성 여부 | 부팅 방식 + 파티션 스타일 조합 | 레거시 경로 혼선 판별 |
| 대상 디스크 버스 | `Get-Disk.BusType` (NVMe/SATA/USB/RAID) | 무엇을 붙이려는지 |
| 저장소 컨트롤러 PCI ID | `Enum\PCI` | 칩셋 세대, VMD/RST 사용 여부 |
| **UEFI 부팅 항목** | `{fwbootmgr}` 열거 | 펌웨어가 그 디스크를 부팅 매체로 아는가 |

### 판정은 두 시점에서 한다

#### ① 사전 판정 — 이사하기 전에

> **사용자**: 이 PC에 M.2 SSD를 달아서 윈도우를 옮기려는데 될까?

| 조건 | 판정 | 조언 |
|---|---|---|
| 펌웨어가 **Legacy 전용** + 대상 NVMe | **지원 안 됨(확정)** | NVMe는 레거시 부팅 옵션롬이 없습니다. SATA SSD를 쓰시거나 메인보드를 바꾸셔야 합니다 |
| UEFI + BIOS **2013년 이전** + NVMe | **지원 안 됨(높은 확신)** | NVMe 부팅이 펌웨어에 들어오기 전 세대입니다 |
| UEFI + BIOS **2014~2018** + NVMe | **불확실 — 확인 필요** | 부팅 메뉴에 그 디스크가 뜨는지 확인해 주세요. 뜨더라도 **전원을 껐다 켜는 부팅**을 반드시 시험해야 합니다 |
| UEFI + BIOS 2019년 이후 + NVMe | **지원(높은 확신)** | 진행 가능 |
| 원본 MBR + 대상 NVMe | **변환 필요** | 클론 후 UEFI 변환이 필요합니다(앱의 자동 변환 옵션) |
| 대상이 USB 연결 | **부팅 대상으로 부적합** | Windows는 USB 부팅을 정식 지원하지 않습니다 |

> **"불확실"을 정직하게 말하는 것이 중요합니다.** B360M Pro4는 2018년 보드였고 부팅 항목도 떴지만
> 실패했습니다. 사양표로 단정하면 틀립니다.

#### ② 사후 진단 — 실패한 뒤, 증상으로 원인을 특정

**이쪽이 훨씬 정확합니다.** 이번 조사에서 확립한 판별 패턴을 규칙으로 넣습니다.

| 증상 | 판정 | 조언 |
|---|---|---|
| **웜 부팅(재시작)은 성공, 콜드 부팅만 실패** | **펌웨어의 장치 초기화 실패** | Fast Boot·ASPM을 끄고 재시도 → 그래도 안 되면 **이 조합은 쓸 수 없습니다.** SATA SSD 또는 메인보드 교체 |
| 부팅 메뉴에 대상 디스크가 **아예 안 뜸** | 펌웨어가 매체로 인식 못 함 | M.2 슬롯 모드·CSM·부팅 항목 수동 추가 → 안 되면 미지원 |
| `bootstat.dat`만 갱신, 하이브·이벤트로그는 그대로 | **커널이 시작조차 못 함** | 부트로더까지만 실행됨. 저장소 드라이버 또는 펌웨어 전송 문제 |
| `0x7B` INACCESSIBLE_BOOT_DEVICE | 저장소 드라이버 미준비 | 하드웨어 독립화(UR) 적용 |
| `0xc0000001` + "After multiple tries" | **부팅 장치 접근 실패** | 파일 손상이면 다른 코드가 납니다. 매체 접근 문제로 보세요 |
| 부팅 관리자 서명이 **2023 PCA**인데 보드가 2018년 이전 | Secure Boot 검증 실패 가능 | Secure Boot를 끄거나 2011 PCA 서명본을 쓰세요 |
| `ntbtlog`가 끝까지 기록됨 | 그 부팅은 **성공**했음 | 실패는 다른 부팅에서 났습니다 |

> 이 표의 첫 줄이 이번 조사의 결론입니다. **웜/콜드 차이 하나로 "펌웨어 문제"가 확정**됩니다.
> 도구가 이걸 물어보고 판정하면 며칠이 몇 분이 됩니다.

### 도구

| 도구 | 입력 | 출력 |
|---|---|---|
| `check_hardware_compatibility` | `targetDeviceNumber?` 또는 예정 사양 | 펌웨어·칩셋·디스크 정보 + **판정(지원/불확실/미지원)** + 근거 + 조언 |

## 3. 하지 않을 것 (Non-goals)

범위가 무한정 커지는 것을 막기 위해 먼저 못 박습니다.

- **Claude가 실행 버튼을 누르는 것** — 제안까지가 전부. 영원히.
- **원격 접속** — 로컬 전용. 네트워크에 열지 않는다.
- **무인 자동화·스케줄링** — 사람이 없는 상태에서 디스크를 쓰지 않는다.
- **파티션 편집(분할·병합·이동)** — 기존 로드맵에서도 정체성 밖으로 판단한 영역.
- **엔진 재구현** — MCP 계층은 얇아야 한다. 판정 로직을 여기서 다시 쓰지 않는다.
- **PE 안에서 Claude를 돌리는 것** — 램디스크 용량·네트워크·인증 전부 문제.
  대신 **진단 파일을 옮기는 오프라인 브리지**로 푼다(§2.5).
- **원격 접속으로 남의 PC를 진단하는 것** — 부팅 안 되는 PC에 네트워크가 있다는 보장이 없고, 위험하다.

## 4. 안전 원칙

> **Claude는 계획하고 설명한다. 지우는 버튼은 사람이 누른다.**

1. **읽기와 쓰기를 계층에서 분리한다.** 진단 도구는 물리적으로 쓰기 경로를 갖지 않는다.
   `[McpServerTool]` 특성을 읽기/쓰기 두 클래스로 나누고, 읽기 클래스는 쓰기 가능한 서비스를 주입받지 않는다.
2. **`SafetyGuard`를 우회할 수 없다.** MCP 계층은 엔진을 호출할 뿐, 안전 판정을 재구현하거나 무력화하지 않는다.
3. **파괴적 작업의 최종 확인은 앱 화면에서 사람이 한다.**
   `SafetyReport.NeedsTypedConfirmation`이 참이면 **모델명 타이핑**을 거쳐야 한다(현행 GUI·CLI와 동일).
4. **되돌릴 수 없는 것은 미리 말한다.** 계획 단계에서 "무엇이 지워지는지"를 Claude가 먼저 설명한다.
5. **모든 MCP 호출을 감사 로그에 남긴다.** 누가·언제·무엇을 요청했는지. 사고 시 재구성 가능해야 한다.
6. **로컬 전용.** 디스크 시리얼·볼륨 레이블은 민감 정보로 다룬다(→ §7).

## 5. 아키텍처

### 5.1 앱이 MCP 서버를 품는다

```
┌─ DiskMigrator.App (관리자 권한, 사용자가 평소처럼 실행) ─┐
│                                                          │
│   WPF UI  ←→  MainViewModel  ←→  엔진(Core/Windows)      │
│                     ↑                                    │
│                     │ 같은 프로세스, 같은 권한            │
│                     ↓                                    │
│   McpHost (Kestrel, 127.0.0.1:<포트> + 토큰)             │
│      ├── ReadOnlyTools   (진단 — 쓰기 서비스 미주입)      │
│      ├── PlanningTools   (계획 — SafetyGuard/ClonePlan)   │
│      └── ProposalTools   (제안 — UI 확인 카드만 띄움)     │
└──────────────────────────┬───────────────────────────────┘
                           │  HTTP + Bearer 토큰
                    Claude Code / Desktop
```

**왜 이 방식인가**

- **UAC 팝업이 없다.** 앱이 이미 관리자 권한이므로 모든 진단이 바로 된다.
  (독립 서버 + 작업별 상승은 대화가 UAC로 계속 끊긴다 — 2026-08-04 조사에서 실제로 겪음)
- **앱 화면과 상태를 공유한다.** 확인 카드를 띄우고, 진행률을 함께 보고,
  "지금 화면에서 디스크 2가 선택돼 있습니다"라고 말할 수 있다.
- **앱이 꺼져 있으면 연결이 안 된다** — 당연하고, 오히려 안전하다.

**기술 선택**

| | 선택 | 이유 |
|---|---|---|
| 패키지 | `ModelContextProtocol.AspNetCore` (공식 C# SDK v2.0) | MS 협업, .NET 8 지원, 특성 기반 도구 등록 |
| 전송 | 로컬 HTTP (Streamable HTTP) | stdio는 프로세스 수명이 Claude에 묶여 부적합 |
| 바인딩 | `127.0.0.1` 고정 | 외부 노출 차단 |
| 포트 | 기본값 + 충돌 시 자동 증가, 실제 포트를 UI에 표시 | |

### 5.2 DTO 계층이 필요하다 ⚠

**엔진 모델을 그대로 노출할 수 없습니다.**

- `ClonePlan.CopyRegion`은 `IBlockDevice`를 품는다 → **직렬화 불가**
- `DiskInfo`는 시리얼·펌웨어까지 들고 있다 → **선별 필요**
- 엔진 모델을 바꾸면 MCP 계약이 깨진다 → **분리해야 안전**

따라서 `DiskMigrator.Mcp` 프로젝트에 **전용 DTO**를 둡니다.
엔진 → DTO 변환은 한 곳(`Mapping.cs`)에 모으고, 여기서 민감 정보 마스킹도 함께 처리합니다.

### 5.3 프로젝트 구성

```
src/
  DiskMigrator.Core        (그대로)
  DiskMigrator.Windows     (그대로)
  DiskMigrator.App         (+ McpHost 시작/중지, 설정 UI)
  DiskMigrator.Mcp    ← 신규
      Dto/            요청·응답 형식
      Mapping.cs      엔진 ↔ DTO (민감정보 마스킹 포함)
      Tools/
        ReadOnlyTools.cs
        PlanningTools.cs
        ProposalTools.cs
      McpHost.cs      Kestrel 수명 관리
      Auth.cs         토큰 발급·검증
      AuditLog.cs     호출 기록
tests/
  DiskMigrator.Mcp.Tests   ← 신규
```

**의존 방향**: `Mcp` → `Core`/`Windows` (단방향). `App` → `Mcp`.
`Core`/`Windows`는 MCP를 모른다 — 그래야 `master`와의 차이가 최소로 유지된다.

## 6. 도구 명세

공통 규칙:
- 모든 응답에 `ok`(bool)과 실패 시 `error{code, message, hint}`
- 크기는 바이트(long) + 사람이 읽는 문자열 동시 제공
- **디스크 지정은 `deviceNumber`(int)** — 드라이브 문자는 바뀌므로 신뢰하지 않는다
- 도구는 **부작용이 없거나(읽기), 제안만 한다(쓰기)**

### 6.1 1단계 — 진단 (읽기 전용) · 위험 0

| 도구 | 입력 | 출력 요지 | 기존 코드 |
|---|---|---|---|
| `list_disks` | — | 디스크 배열: 번호·모델·크기·버스·파티션스타일·시스템/부팅/페이지파일 여부·오프라인·읽기전용 | `WindowsDiskService` |
| `inspect_disk` | `deviceNumber` | 파티션 배열(오프셋·크기·타입·파일시스템·레이블·문자·사용량), GPT GUID/MBR 서명 | `DiskLayoutMap`, `NtfsUsageProbe` |
| `check_boot_readiness` | `deviceNumber` | `BootCheckItem[]`(이름·통과여부·심각도·상세·코드) + 종합 판정 | `BootReadinessCheck` |
| `read_boot_drivers` | `deviceNumber` | Start=0 드라이버 전수 + **파일 존재 여부** + 표준 위치 밖 표시 | `RegistryHive`, `ThirdPartyBootDriverScan` |
| `read_fast_startup` | `deviceNumber` | `HiberbootEnabled`·`HibernateEnabled`·`hiberfil.sys` 유무·크기 | `UniversalRestore` 진단부 |
| `audit_esp` | `deviceNumber` | ESP 파일 목록·BCD 덤프·**부팅 관리자 서명 발급자** | 신규 |
| `inspect_image` | `path` | VHDX 구조·파티션·볼륨별 chkdsk 결과·사슬(부모) 정보 | `ImageInspector` |
| `analyze_boot_trace` | `deviceNumber` | 부팅 관련 파일 타임스탬프 → **커널이 어디까지 갔는지** 판정 | 신규 |
| `snapshot_state` | `deviceNumber`, `tag` | 서비스·BCD·ESP·드라이버 상태를 저장 | 신규 |
| `diff_state` | `tagA`, `tagB` | 두 스냅샷의 차이 | 신규 |
| `check_hardware_compatibility` | `targetDeviceNumber?` | 펌웨어·칩셋·디스크 + **판정(지원/불확실/미지원)**·근거·조언 (§2.6) | 신규 |
| `diagnose_boot_symptom` | 증상 + 리포트 | 증상 기반 원인 특정 — 웜/콜드 차이 등 (§2.6) | 신규 |
| `save_diagnostic` | `deviceNumber`, `path` | 진단 리포트 파일 저장(§2.5 경로 B) | 신규 |
| `load_diagnostic` / `diff_diagnostics` | `path` (+`pathB`) | 리포트 읽기·전후 비교 | 신규 |

> `audit_esp`·`analyze_boot_trace`·`snapshot_state`/`diff_state`는 이번 조사에서
> 손으로 만든 스크립트를 제품 코드로 옮기는 것입니다. **그 자체로 수동 버전에도 가치가 있으므로,
> 엔진 쪽 구현은 `Core`/`Windows`에 두어 나중에 `master`로 역이식할 수 있게 합니다.**

### 6.2 2단계 — 계획·조언 · 쓰기 없음

| 도구 | 입력 | 출력 요지 |
|---|---|---|
| `evaluate_safety` | `sourceNumber`, `targetNumber`, `useSnapshot?` | `canProceed`, `needsTypedConfirmation`, `issues[]`(심각도·코드·메시지) |
| `plan_clone` | `sourceNumber`, `targetNumber`, 옵션 | 복사 구간 요약(무엇이 어디로·총량), 축소/확대 필요 여부, 예상 시간 |
| `explain_boot_failure` | `deviceNumber` | 1단계 진단들을 엮은 원인 후보 + 다음 조치(우선순위 순) |

`plan_clone`은 `ClonePlan`을 만들되 **DTO로 요약해서** 돌려줍니다(§5.2).

```
  │                    → 카드 사라짐                  │
  │                                                   │
  │                  ③ 모델명 타이핑 ←────────────────┤  2차 관문
  │                    → 시작 버튼 활성               │      (기존 그대로)
  │                                                   │
  │                  ④ 시작 버튼 ←────────────────────┤
  │                                                   │
  └─ get_progress ──→ 진행률 관찰(읽기)               │
```

**`ConfirmationText`(모델명 입력란)는 Claude가 어떤 경로로도 건드릴 수 없다.**
이 한 줄이 무너지면 나머지 설계는 전부 의미가 없다. 제안 적용은 원본·대상·옵션까지만 채운다.

#### 왜 값을 바로 채우지 않는가

곧바로 채우면 사용자가 자리를 비운 사이 화면의 선택이 바뀌어 있게 된다. 돌아온 사용자는
그것이 자기가 고른 것인지 Claude가 고른 것인지 알 수 없고, 그 상태에서 모델명만 입력하면
의도하지 않은 디스크를 지울 수 있다. **[적용]을 한 번 거치면 "내가 받아들인 제안"이 된다.**

#### 제안의 수명

| 상태 | 뜻 |
|---|---|
| `Pending` | 카드가 떠 있고 사용자 반응을 기다리는 중 |
| `Applied` | 사용자가 적용함(아직 실행 전 — 모델명 입력이 남아 있다) |
| `Dismissed` | 사용자가 무시함 |
| `Superseded` | 새 제안이 덮어씀 |
| `Expired` | 디스크 구성이 바뀌었거나 10분이 지남 |

- **디스크가 바뀌면 무효화한다** — 기존 `AssertTargetUnchanged`(모델·시리얼·크기 대조)를 재사용한다.
  제안을 만든 뒤 사용자가 USB를 바꿔 꽂았을 수 있다.
- **10분이 지나면 만료한다** — 오래된 제안을 무심코 적용하는 것을 막는다.
- **새 제안은 기존 것을 덮어쓴다**(`Superseded`). 카드가 쌓이면 사용자가 어느 것을 보는지 알 수 없다.

#### 제안이 거절되는 경우

| 상황 | 응답 |
|---|---|
| 앱이 작업 중(`Stage != Selecting`) | `BUSY` — 진행률 조회만 허용 |
| `SafetyGuard`가 차단 | `BLOCKED` + 차단 사유 — **애초에 카드를 띄우지 않는다** |
| 디스크가 없음 | `DISK_NOT_FOUND` |
| 통로가 꺼져 있음 | (연결 자체가 안 됨) |

차단된 조합은 제안조차 하지 않는다. 사용자에게 "적용해도 실행할 수 없는 카드"를 보여주는 것은
혼란만 준다. Claude는 `evaluate_safety`로 먼저 확인하고, 차단 사유를 사용자에게 설명해야 한다.

#### 카드는 어디에 뜨는가

**전역 배너** — 업데이트 알림과 같은 자리. Assistant 탭 안에 두면 다른 화면을 보고 있는 사용자가
제안이 온 것을 모른다. 모달 대화상자는 쓰지 않는다 — 강제로 답을 요구하면 사용자가 내용을 읽지 않고
누르게 된다.

카드에 담을 것: **무엇을**(원본→대상), **왜**(Claude가 준 이유), **안전 요약**(확인 필요 여부),
그리고 [적용] [무시].

#### 도구

| 도구 | 하는 일 | 게이트 |
|---|---|---|
| `propose_clone` | 제안 카드를 띄운다. **아무것도 채우지 않는다** | 적용 + 모델명 |
| `propose_backup` | 디스크 → 이미지 파일. 디스크는 읽기만 한다 | 적용 + 시작 |
| `propose_restore` | 이미지 파일 → 디스크. **대상이 지워진다** | 적용 + 모델명 |
| `propose_boot_repair` | 대상 디스크의 부팅 구성을 고친다(데이터는 지우지 않음) | 적용 + 시작 |
| `get_proposal_status` | 제안이 어떻게 됐는지 조회(읽기) | 없음 |
| `get_progress` | 진행률·구간·ETA·속도(읽기) | 없음 |
| `cancel_operation` | 진행 중 작업 취소 요청 | 없음(안전한 방향) |

#### 확장하며 새로 세운 금지선 (2026-08-05)

`propose_clone`이 실기 게이트 검증을 통과한 뒤 나머지 셋을 같은 틀로 확장했다. 다만
**같은 틀이라고 같은 규칙이 그대로 적용되지는 않는다** — 확장하면서 드러난 차이가 있다.

| 종류 | 원본 | 대상 | `SafetyGuard`가 그대로 듣는가 |
|---|---|---|---|
| 복제 | 디스크 | 디스크 | 그렇다 |
| 백업 | 디스크 | **파일** | 아니다 — 대상 파괴 규칙이 걸릴 곳이 없다(읽기만 하므로 무해) |
| 복원 | **파일** | 디스크 | **아니다 — 넘길 원본 디스크가 없다.** 대상 자체의 금기를 따로 확인한다 |
| 부팅 복구 | — | 디스크 | 아니다 — 지우지 않는다. 대신 **실행 중인 시스템 디스크를 거절**한다 |

- **복원의 금지선**(`SafetyGuard`를 못 쓰는 자리에 직접 세움):
  시스템 디스크 · 부팅 디스크 · 페이지파일 보유 · 읽기 전용 → `BLOCKED`, 카드조차 띄우지 않는다.
  이미지 파일이 없으면 `FILE_NOT_FOUND`. **복원이 중간에 실패하면 대상은 이미 지워진 뒤**이므로
  시작 전에 막아야 한다.
- **부팅 복구의 금지선**: 이 앱이 돌아가고 있는 디스크는 `LIVE_SYSTEM_DISK`로 거절한다.
  이미 부팅에 성공한 디스크이고, 하이브도 잠겨 있다.
- **백업의 안내 의무**: 경로에 파일이 이미 있으면 앱이 **증분 사슬로 잇는다.** "새로 백업한다"고
  생각한 자리에서 사슬에 붙으면 원본이 망가졌을 때 사슬 전체가 못 쓰게 되므로, 도구 응답에
  그 사실을 담아 Claude가 사용자에게 옮기게 한다.
- **카드의 양 끝은 종류마다 다르다.** 복제 전용으로 `Source.DeviceNumber`를 바인딩해 두면
  백업·복원 카드에서 한쪽이 빈칸이 된다 — **어느 디스크가 지워지는지 안 보이는 카드**가 된다.
  `CloneProposal.Endpoints`가 종류에 맞는 양 끝을 만든다.

**제안 도구의 반환값은 "실행 결과"가 아니라 "제안이 화면에 떴다"이다.**
사용자가 누르기 전까지 아무 일도 일어나지 않는다.

#### 이 단계에서 반드시 시험할 것

- Claude가 `ConfirmationText`를 채우거나 시작을 유발할 수 있는지 **적대적으로** 시도 → 전부 실패해야 한다
- 제안 후 대상 디스크를 뽑았다 다시 꽂으면 → 제안이 무효화되어야 한다
- 작업 중 제안 → `BUSY`
- 차단 조합 제안 → 카드가 뜨지 않아야 한다

**상태(2026-08-05).** 위 넷은 자동 시험(`ProposalGateTests`)과 **실기 게이트 검증**으로 확인했다 —
차단 조합은 카드 없이 거절, 유효한 제안은 카드 → [적용] → 폼은 채워지되 "확인 필요"에서 멈춤,
`get_progress`는 `Running: false`, `get_proposal_status`는 `Applied` + "아직 실행되지 않았다".

확장한 셋(`propose_backup`·`propose_restore`·`propose_boot_repair`)도 실기로 확인했다(2026-08-05).

| 확인한 것 | 결과 |
|---|---|
| 부팅 복구 → 실행 중인 시스템 디스크 | `LIVE_SYSTEM_DISK`, 카드 없음 |
| 복원 → 실행 중인 시스템 디스크 | `BLOCKED`(SYSTEM+BOOT+PAGEFILE), 카드 없음 |
| 복원 → 없는 이미지 / 없는 디스크 | `FILE_NOT_FOUND` / `DISK_NOT_FOUND` |
| 복제 0→0, 복제 → 시스템 디스크 | `INVALID_ARGUMENT` / `BLOCKED` |
| 이유 없는 제안(전 종류) | `INVALID_ARGUMENT` |
| 백업·복원·부팅 복구 카드 | 종류 표시·양 끝·경고 수위 모두 정상 |
| 부팅 복구 [적용] | 화면 전환 + 대상 선택, **모델명 입력란은 그대로** |

**남은 것**: `propose_backup`·`propose_restore`의 [적용] 경로는 아직 눌러 보지 않았다
(자동 시험과 코드로만 확인). 되돌릴 수 없는 쪽이므로 실기로 한 번 더 볼 것.

#### 확장 검증 중에 드러난 결함 (2026-08-05, 모두 수정)

제안 게이트와 무관하게, **실기로 돌려 보지 않았으면 못 찾았을 것들**이다.

| 결함 | 어디가 문제였나 |
|---|---|
| `IsOffline`이 하드코딩 `false` | 엔진은 같은 IOCTL을 **이미 쓰고 있었다**(`DiskOfflineScope`가 클론 전 대상을 오프라인으로 내림). 읽는 법을 몰라서가 아니라 *보고하는 자리*에만 `false`가 박혀 있었다. 소비처가 `DiskInfo.cs` 한 줄뿐이라 아무도 틀렸다는 걸 몰랐다 |
| 오프라인을 부팅 결함으로 읽음 | 오프라인 디스크는 ESP도 Windows 폴더도 "없는 것처럼" 보인다. 멀쩡한 디스크에 부팅 복구를 하겠다고 덤빌 수 있는 자리 → `DISK_OFFLINE`을 확정 원인으로 먼저 낸다 |
| [적용] 후 목록이 스크롤되지 않음 | 선택은 됐지만 화면 밖. **무엇에 동의했는지 눈으로 확인할 수 없으면 확인 카드의 뜻이 없다** |

앞의 둘은 `Core`/`Windows` 변경이라 **master의 v1.4.1에도 있는 결함**이다. 백포트는 미결정.

## 8. 단계별 완료 기준 (DoD)

각 단계는 **실기 검증을 거쳐야** 다음으로 넘어갑니다. 이 프로젝트의 기존 방식대로.

### 1단계 완료 조건
- [ ] 시나리오 **S2**(부팅 실패 진단)를 Claude가 도구만으로 끝까지 수행
- [ ] 시나리오 **S3**(이미지 무결성)을 정상·손상 이미지 양쪽으로 확인
- [ ] 시나리오 **S5**(부팅 불가 PC — 진단 파일 왕복)를 PE에서 실기 수행
- [ ] **이번 조사의 결론에 도구만으로 도달하는지 검증** — 같은 M.2를 연결해
      `analyze_boot_trace` + `diagnose_boot_symptom`으로 "펌웨어 콜드 부팅 문제"가 나오는가.
      **이것이 1단계의 진짜 시험지입니다.** 며칠 걸린 판단을 도구가 재현해야 합니다
- [ ] `check_hardware_compatibility`가 이 PC(B860, 2025 BIOS)는 "지원",
      B360M Pro4는 "불확실 또는 미지원"으로 판정하는지
- [ ] 모든 진단 도구가 **쓰기 서비스를 주입받지 않음**을 테스트로 보장
- [ ] 진단 리포트 저장이 **대상 디스크에 아무것도 쓰지 않음**을 전후 해시로 확인
- [ ] 앱을 끄면 연결이 끊기고, 재시작하면 새 토큰이 필요함을 확인

### 2단계 완료 조건
- [ ] 시나리오 **S1**의 1~4단계(진단→안전성→계획)를 근거와 함께 설명
- [ ] `evaluate_safety`가 GUI와 **완전히 같은 판정**을 내림(같은 입력·같은 코드)
- [ ] 대상이 더 작은 경우/더 큰 경우/MBR·GPT 혼합 등 경계 조합 검증

### 3단계 완료 조건
- [ ] 시나리오 **S1**을 처음부터 끝까지(부팅 확인 포함) 실기 수행
- [ ] **Claude가 사용자 확인 없이 쓰기를 유발할 수 없음**을 시도해서 확인(적대적 테스트)
- [ ] 진행 중 취소·오류·중단이 앱과 Claude 양쪽에서 일관되게 보임

## 10. 테스트 전략

- **단위**: DTO 매핑(마스킹 포함), 토큰 검증, 도구 인자 검증 — 디스크 없이 가능
- **계약**: 각 도구의 입출력 스키마 고정. 엔진 모델이 바뀌어도 계약이 유지되는지
- **격리 보장**: 읽기 도구 클래스가 쓰기 서비스를 **컴파일 시점에** 못 받게 설계하고, 테스트로 재확인
- **적대적**: "확인 없이 지워라"는 요청으로 3단계 게이트를 뚫으려 시도 → 반드시 실패해야 함
- **실기**: VHD 가상 디스크로 S1~S4 전체. 기존 `DiskMigrator.VhdTest` 자산 활용

| 상태 | 실기 검증 완료, 유지보수만 | 개발 중 |
| 릴리스 | **최신 하나는 계속 유지한다**(현재 v1.4.2) | 완성 시 **v1.0.0** |

> **관례 변경**: 지금까지는 GitHub 릴리스를 최신 하나만 남겼지만,
> **수동 버전의 최신 릴리스는 DiskMigrator-X가 나와도 지우지 않는다.** 수동 버전을 계속 쓸 수 있어야 한다는 요구.
> (수동 버전 *계열 안에서*의 교체는 관례대로 — 2026-08-05 v1.4.2를 내며 v1.4.1 릴리스는 삭제했다. git 태그는 보존.)

> **버전은 1.0.0부터 시작한다**(사용자 지정, 2026-08-05). 수동 버전의 1.4.x를 이어받지 않는다 —
> 별개 제품이므로 번호도 새로 센다.

#### ⚠ 이 두 가지가 **아직 구현되지 않아 실제로 오작동 중이다** (2026-08-05 확인)

**1. 업데이트 배너가 남의 릴리스를 알린다.** `UpdateChecker`가 `withoz/DiskMigrator`의
`releases/latest`를 그대로 보므로, X를 띄우면 *"새 버전이 있습니다 1.4.2 [다운로드]"* 가 뜬다.
누르면 **다른 제품**을 받는다. 게다가 X가 1.0.0으로 시작하면 태그 비교상 **영원히**
"새 버전이 있다"가 된다(1.0.0 < 1.4.x). 버전만 바꿔서는 해결되지 않고, X 전용 릴리스 채널
(예: 태그 접두사 `x-v1.0.0`)이나 확인 자체를 끄는 결정이 필요하다.

**2. 설정·로그가 이미 섞였다.** 아래 분리 표는 계획일 뿐 미구현이라 두 앱이
`%LocalAppData%\DiskMigrator`의 **같은 로그 파일**에 쓴다. 오늘 그 파일 하나에
X의 `MCP propose_*` 186줄과 수동 버전의 `부팅 구성 검사` 10줄이 함께 남았다.
"문제를 신고받았을 때 어느 앱인지 알 수 없다"던 우려가 이미 현실이 됐다.

**두 앱은 공존한다.** 제품명이 다르므로 설치 경로·시작 메뉴 항목·설정 저장 위치를 모두 분리한다:

| | DiskMigrator (v1.x) | DiskMigrator-X |
|---|---|---|
| 설치 경로 | `%ProgramFiles%\DiskMigrator` | `%ProgramFiles%\DiskMigrator-X` |
| 실행 파일 | `DiskMigrator.exe` | `DiskMigratorX.exe` |
| 설정·로그 | `%LocalAppData%\DiskMigrator` | `%LocalAppData%\DiskMigrator-X` |
| MCP 서버 이름 | (없음) | `DiskMigrator-X` |

> 설정과 로그까지 나누는 이유: 두 앱이 같은 폴더를 쓰면 한쪽의 언어 설정이나 EULA 동의가
> 다른 쪽에 새고, 로그가 섞여 문제를 신고받았을 때 어느 앱의 것인지 알 수 없게 됩니다.

**역이식**: 진단 엔진(`BootDriverInventory`·`BootTraceAnalysis`·`FastStartupState` 등)은
수동 버전에도 유용하므로 `Core`/`Windows`에 구현한다. 안정화되면 `master`로 가져간다 —
저장소가 하나라 `git cherry-pick`으로 끝난다.

## 12. 진행 순서

1. `DiskMigrator.Mcp` 프로젝트 + DTO/매핑 뼈대 (디스크 없이 테스트 가능한 부분부터)

5. 2단계 DoD 통과 → 3단계 게이트 설계를 **다시 합의**한 뒤 착수
