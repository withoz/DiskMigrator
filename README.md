# DiskMigrator

Windows용 디스크 전체 클론 도구. 실행 중인 시스템 디스크를 포함해 디스크를 섹터 단위로 복제합니다.

.NET 8 · WPF · MIT 라이선스

---

## ⚠️ 경고 — 먼저 읽으십시오

**이 프로그램은 대상 디스크의 모든 데이터를 영구히 삭제합니다. 실수하면 되돌릴 수 없습니다.**

- 사용 전에 **반드시 중요한 데이터를 백업**하십시오.
- 대상 디스크를 고를 때 모델명과 용량을 **두 번 확인**하십시오.
- 이 소프트웨어는 **아무런 보증 없이 "있는 그대로"** 제공됩니다. 데이터 손실에 대해 제작자는 책임지지 않습니다 ([LICENSE](LICENSE) 참조).

## 안전장치

디스크를 통째로 날릴 수 있는 도구이므로, 안전 검사가 이 프로젝트의 중심입니다.

**절대 차단 — 어떤 확인으로도 진행할 수 없습니다:**

- 대상이 현재 실행 중인 Windows가 설치된 **시스템 디스크**인 경우
- 대상이 이 PC의 **부팅 파티션**을 가진 디스크인 경우
- 대상에 **페이지 파일**이 있는 경우
- 원본과 대상이 **같은 디스크**인 경우
- 대상 용량이 원본보다 **작은** 경우
- 원본과 대상의 **논리 섹터 크기가 다른** 경우
- **관리자 권한**이 없는 경우

**사용자 확인 요구:**

- 대상에 기존 파티션이 있으면, 사용자가 **대상 디스크의 모델명을 직접 타이핑**해야 진행됩니다.

**쓰기 직전 재확인:**

작업을 시작하는 순간 디스크를 다시 열거해, 사용자가 확인한 그 디스크가 지금도 같은 물리 디스크인지 검사합니다 (모델·시리얼·용량 대조). USB를 뽑았다 꽂으면 장치 번호가 재배정되므로, 번호만 믿으면 엉뚱한 디스크를 지울 수 있습니다.

시스템 디스크 판별은 WMI가 아니라 커널에 직접 묻습니다 (`IOCTL_VOLUME_GET_VOLUME_DISK_EXTENTS`). 부팅 디스크는 `HKLM\SYSTEM\Setup\SystemPartition` 값으로 판별합니다 — "EFI 파티션이 있는 디스크"로 판단하면, 예전에 Windows가 깔려 있던 디스크를 재활용하려는 정상적인 경우가 차단되기 때문입니다.

## 실행 중인 시스템 디스크는 어떻게 복제하는가

지금 부팅되어 쓰고 있는 디스크를 그냥 읽으면, 읽는 몇십 분 동안 파일이 계속 바뀝니다. 결과물은 "앞부분은 10시 상태, 뒷부분은 10시 40분 상태"인 뒤죽박죽이 되어 대개 부팅되지 않습니다.

DiskMigrator는 **VSS(볼륨 섀도 복사본)** 로 그 시점에 정지된 이미지를 만들어 복제합니다. 그런데 VSS는 *볼륨* 스냅샷이지 *디스크* 스냅샷이 아니므로, 디스크 이미지를 조각으로 나눠 각 조각을 알맞은 곳에서 읽습니다:

```
 [MBR/GPT 헤더]  [파티션1: EFI]  [간격]  [파티션2: C:]  ...  [GPT 백업 헤더]
      원시           원시*        원시      스냅샷              원시
```

\* EFI 시스템 파티션은 FAT32라 VSS가 지원하지 않습니다. 클론 중에 바뀌지 않으므로 원시로 읽어도 안전합니다.

파티션 테이블도 클론 도중 바뀌지 않으므로 원시로 읽습니다.

## 대상 디스크는 왜 오프라인으로 내리는가

원본을 스냅샷으로 얼려도, **대상 쪽에서 정합성이 깨질 수 있습니다.**

클론이 대상에 파티션 테이블을 쓰는 순간, 대상에는 원본과 똑같은 NTFS 볼륨이 생깁니다. 대상 디스크가 온라인 상태이면 Windows가 이 볼륨들을 **자동 마운트**하고 NTFS 로그를 재생하는데, 클론이 도는 내내 우리가 복사해 넣은 데이터 위에 계속 씁니다.

이건 가정이 아니라 실기에서 관측한 사실입니다. 931GB 클론에서 파일 시스템이 있는 영역에만 **불일치 617,692건**이 생겼고, 파일 시스템이 없는 MSR 영역에는 한 건도 없었습니다. 이벤트 로그에도 `partmgr 이벤트 58: "디스크 서명이 같습니다"`가 남았습니다 — Windows가 대상 볼륨을 인식하고 손대고 있었다는 증거입니다.

그래서 DiskMigrator는 대상에 쓰기 전에 디스크를 **오프라인으로 내립니다**(`IOCTL_DISK_SET_DISK_ATTRIBUTES` + `DISK_ATTRIBUTE_OFFLINE`). 오프라인 디스크는 볼륨이 표면화되지 않아 자동 마운트도 로그 재생도 일어나지 않지만, 원시 섹터 쓰기는 그대로 됩니다. 클론·검증·GPT 보정이 모두 끝난 뒤에야 다시 온라인으로 올립니다.

> **볼륨 잠금만으로는 부족합니다.** `FSCTL_LOCK_VOLUME`은 *이미 존재하는* 볼륨만 막지, 클론 중에 *새로 생기는* 볼륨은 막지 못합니다. 대상이 빈 디스크였다면 잠글 볼륨이 애초에 없고, 그래서 이 문제가 생겼습니다.

이 버그는 검증(`--no-verify`를 켜지 않는 한 기본 동작)이 잡아냈습니다. 검증이 없었다면 손상된 디스크를 "성공"으로 보고했을 것입니다. VHD 테스트에서 안 걸린 이유는 VHD 클론이 0.25초 만에 끝나 Windows가 반응할 시간이 없었기 때문입니다 — 빠른 테스트의 통과가 느린 실전의 통과를 보장하지 않는다는 교훈입니다.

## GPT 백업 헤더 보정

GPT는 디스크 **끝**에 헤더 사본을 둡니다. 섹터 단위로 그대로 복제하면 이 백업 헤더는 "원본 디스크의 끝"이었던 자리에 놓이는데, 대상이 더 크면 그 자리는 디스크 중간입니다. 그러면:

- 디스크 관리가 "GPT 백업 헤더가 잘못된 위치에 있다"고 보고하고,
- 남는 공간을 쓸 수 없으며,
- 일부 UEFI 펌웨어는 부팅을 거부합니다.

DiskMigrator는 복제가 성공하면 백업 헤더를 진짜 디스크 끝으로 옮기고, `LastUsableLBA`·CRC32·보호 MBR을 다시 계산합니다. 그 뒤 디스크 관리에서 마지막 파티션을 남는 공간까지 확장할 수 있습니다.

## 긴 클론과 스냅샷 붕괴 — 섀도 저장소 확보

VSS 스냅샷은 copy-on-write입니다. 스냅샷을 뜬 뒤 원본 볼륨에 쓰기가 일어날 때마다, 원래 블록이 **diff 영역(섀도 저장소)** 으로 복사되어 그 시점 데이터를 보존합니다. diff 영역이 꽉 차면 VSS는 스냅샷을 무효화하고, 그때부터 스냅샷 읽기가 **라이브 데이터를 반환**합니다.

실기에서 이 문제를 정확히 관측했습니다. 느린 QLC SSD 대상(약 90MB/s) 때문에 931GB 클론이 3시간 걸렸고, 그동안 C:에 쌓인 쓰기가 기본 섀도 저장소 한도를 넘겨 스냅샷이 붕괴했습니다. 증거:

- 클론 디스크의 한 오프셋에는 **유효한 데이터**(스냅샷 시점의 JSON 설정 파일)가 있었는데,
- 같은 오프셋의 라이브 디스크는 **전부 0**이었습니다 (그 사이 파일이 삭제됨).
- 즉 복제 초반엔 스냅샷이 올바른 데이터를 줬고 클론이 정확히 복사했지만, 검증 시점(2.5시간 후)엔 같은 스냅샷이 라이브 데이터(0)를 반환해 가짜 불일치가 났습니다.

그래서 DiskMigrator는 스냅샷을 뜨기 전에 각 볼륨의 섀도 저장소 최대 크기를 **볼륨의 20%, 최소 40GB**로 확보합니다(`IVssDifferentialSoftwareSnapshotManagement.ChangeDiffAreaMaximumSize`). 긴 클론 동안의 쓰기를 견디기 위함입니다.

### 검증은 "복제 중 기록한 해시"와 대상을 비교합니다

검증의 목적은 **대상 디스크가 우리가 쓴 바이트를 그대로 보존했는가**(매체 불량·쓰기 오류 탐지)입니다. 그래서 복제하면서 각 블록에 실제로 쓴 데이터의 해시(XxHash128)를 기록해 두고, 검증 때 **대상만** 다시 읽어 그 해시와 비교합니다. 원본(스냅샷)은 다시 읽지 않습니다.

**왜 원본을 다시 안 읽는가 — 실기에서 규명한 VSS 드리프트:**

처음엔 검증이 원본(스냅샷)을 다시 읽어 대상과 비교했는데, VSS 스냅샷 클론에서 계속 소수의 불일치가 났습니다. 측정으로 원인을 밝혔습니다:

1. VSS 스냅샷은 원래 불변이어야 하지만, 실행 중인 C:의 스냅샷을 90초 간격으로 두 번 읽으니 **3.28GB가 바뀌어** 있었습니다 (볼륨 전역에 흩어져서).
2. 즉시 재읽기(back-to-back)는 완전히 일치 → 읽기 방식 문제가 아니라 **진짜 시간 드리프트**.
3. 원인: **클라이언트 Windows(10/11)는 VSS 섀도 저장소(diff 영역)를 다른 볼륨에 둘 수 없습니다**(Server 전용 기능). 그래서 diff 영역이 스냅샷 대상 볼륨 자신에 놓이고, VSS는 자기 diff 영역을 스냅샷에서 제외하므로, 그 블록을 읽으면 자라나는 diff 데이터가 보여 드리프트합니다.
4. 이 드리프트는 `System Volume Information`의 VSS 임시 스크래치라 **무해**합니다 (클론에 있어도 부팅 무관, Windows가 정리). 하지만 원본 재읽기 검증은 이를 가짜 불일치로 잡습니다.

그래서 검증을 "움직이는 원본과 비교"가 아니라 "복제 때 쓴 것과 대상을 비교"로 바꿨습니다. 상용 백업 도구들의 방식이며, 드리프트에 면역이면서 진짜 쓰기 오류는 정확히 잡습니다.

## 빌드

```bash
# 요구사항: .NET 8 SDK 이상 (또는 net8.0 타깃을 빌드할 수 있는 최신 SDK)
dotnet build DiskMigrator.slnx

# 테스트 (실제 디스크를 건드리지 않습니다)
dotnet test

# 배포용 단일 exe — 런타임이 없는 PC에서도 실행됩니다
dotnet publish src/DiskMigrator.App -c Release -o publish
```

`app.manifest`에 `requireAdministrator`가 걸려 있어 실행 시 UAC 상승을 요구합니다. 원시 디스크 접근·볼륨 잠금·VSS 스냅샷 모두 관리자 권한이 필요합니다.

### 진단 도구

실제 하드웨어에서 저수준 계층이 올바로 동작하는지 확인합니다. **읽기만 하며 어떤 디스크에도 쓰지 않습니다.**

```bash
dotnet run --project tools/DiskMigrator.Probe
```

네이티브 구조체 크기 검증, 디스크 열거 결과, 그리고 모든 원본→대상 조합에 대한 SafetyGuard 판정을 출력합니다. 클론을 시도하기 전에 이 출력으로 **시스템 디스크가 정확히 식별되는지** 반드시 확인하십시오.

## 구조

위험한 저수준 코드와 UI를 격리하고, 실제 디스크 없이 엔진을 테스트할 수 있게 나눴습니다.

```
src/
  DiskMigrator.Core/       플랫폼 독립 — 여기에 IBlockDevice 추상화가 있습니다
    Abstractions/          IBlockDevice, IDiskService, ISnapshotProvider
    Safety/                SafetyGuard — 대상 검증 규칙 (이 프로젝트의 마지막 방어선)
    Engine/                CloneEngine, Verifier, ClonePlan, 진행률
    Partitioning/          GptRepair, Crc32
    Devices/               FileBlockDevice (테스트 및 이미지 파일용)
  DiskMigrator.Windows/    Win32 P/Invoke
    Interop/               NativeMethods, 구조체, IOCTL
    Devices/               RawDiskDevice, VolumeLock, 디스크 열거
    Snapshots/             VssSnapshotProvider (AlphaVSS)
    Jobs/                  CloneOrchestrator — 순서를 책임집니다
  DiskMigrator.App/        WPF (MVVM)
tests/
  DiskMigrator.Core.Tests/ 실제 디스크 없이 엔진 전체를 검증
tools/
  DiskMigrator.Probe/      읽기 전용 하드웨어 진단
  DiskMigrator.VhdTest/    VHD 대상 클론 통합 테스트 (가상 디스크에만 씀)
  vhd-clone-test.ps1       VHD 생성 → 클론 → 결과 검증 → 정리
```

핵심 설계는 `IBlockDevice`입니다. 클론 엔진은 이 인터페이스만 알기 때문에, 파일이나 메모리 기반 가짜 장치로 불량 섹터·취소·검증 실패까지 전부 테스트할 수 있습니다. "위험한 코드를 안전하게 테스트한다"는 것이 이 구조의 목적입니다.

## 검증 현황 (정직하게)

이 부류의 도구는 "빌드된다"와 "믿을 수 있다" 사이의 거리가 멉니다. 지금까지 실제로 확인된 것과 아닌 것을 구분해 둡니다.

**실제 하드웨어에서 검증됨** (Windows 11, NVMe 1대 + USB 4대):

- 네이티브 구조체 레이아웃이 Win32 헤더와 일치 (크기 8종 대조)
- 디스크 열거 — 모델·용량·시리얼·버스·파티션·EFI 파티션 식별
- 시스템/부팅/페이지 파일 디스크 판별 (오탐·누락 없음)
- SafetyGuard 판정 — 모든 원본→대상 조합에서 기대대로 동작
- **원시 디스크 읽기 경로** — `FILE_FLAG_NO_BUFFERING` + 정렬 버퍼 조합, 섹터 0 / 마지막 섹터 / 디스크 끝 너머 경계 처리, NVMe에서 4.5 GB/s

**가상 디스크(VHD)로 end-to-end 검증됨** — `tools/vhd-clone-test.ps1`, 오프라인·VSS 두 모드 모두:

- **원시 디스크 쓰기 경로** — 1GB → 2GB 클론 완료
- **볼륨 잠금 / 마운트 해제** — 기존 NTFS 볼륨이 있는 대상을 잠그고 디스마운트한 뒤 덮어쓰기
- **VSS 스냅샷** — 스냅샷 생성 → 스냅샷 장치에서 파티션 데이터 읽기 → 스냅샷 삭제
- **검증 단계** — 원본과 대상 재비교 통과
- **GPT 백업 헤더 보정** — 백업 헤더를 디스크 끝으로 이동, 보호 MBR 갱신.
  클론 후 Windows가 대상을 `Healthy`/`GPT`로 인식하고 남는 1GB를 미할당으로 정상 표시
- **데이터 정합성** — 디스크 GUID가 원본과 일치(섹터 단위 복제 확인), 볼륨 레이블 일치,
  테스트 파일 6개 SHA-256 전부 일치, 대상의 기존 데이터는 정상적으로 사라짐

**실제 시스템 디스크(C:)에서 계획 단계까지 검증됨** — `--plan-only` 모드, 쓰기 없음:

실제 레이아웃(EFI FAT32 200MB + MSR 16MB + C: NTFS 930GB + 복구 NTFS 826MB)에서:

- VSS가 NTFS 볼륨 2개(C:, 복구)를 **하나의 일관된 스냅샷 세트**로 생성
- FAT32인 EFI 파티션과 RAW인 MSR은 VSS 대상이 아니므로 원시 복사로 정확히 분류
- 두 스냅샷 모두에서 "마지막 4,096바이트를 못 읽는" 현상이 재현되었고, 읽기 가능 길이 탐색이 처리
- 복사 구간 8개가 디스크 전체 `[0 .. 1,000,204,886,016)`를 **구멍·겹침 없이** 덮음
- 모든 구간의 시작/중간/끝 24개 지점이 실제로 읽힘

**실제 시스템 디스크 전체 클론 + 실제 부팅 성공** — 최종 목적 달성 (v0.1.2):

실행 중인 Windows 시스템 디스크(약 216GB 사용, BIOS/MBR + 복구 파티션)를 VSS 스냅샷으로
클론해 별도 SSD에 옮긴 뒤, **원래 PC에서 원본을 빼고 클론 디스크로 실제 부팅에 성공**했습니다.

- VSS가 실행 중 C:와 복구 볼륨을 스냅샷 → 스냅샷에서 파티션 데이터 복사
- 복제-중-해시 검증 통과 (아래 참조)
- 클론 후 NTFS `dirty` 비트 없음(파일시스템 무결), 레지스트리 SYSTEM 하이브 정상, 활성 파티션 설정, bootmgr·BCD·ntoskrnl·winload 전부 존재
- **동일 하드웨어에서 로그인 화면까지 정상 부팅** — 부팅 가능한 완전한 사본임을 실증

여기에 이르기까지 실기에서 세 종류의 실패를 검증 기능이 걸러냈고(단일 exe VSS 미로드, 무스냅샷
폴백, VSS 스냅샷 드리프트), 각각을 로그·측정으로 규명해 고쳤습니다. 자세한 내용은 커밋 이력 참조.

**단위 테스트로 검증됨** (실제 디스크 없이, 80개 테스트):

- 클론 엔진 — 바이트 단위 정확성, 대상이 더 클 때 뒤쪽 영역 보존
- 불량 섹터 — 재시도 복구, 섹터 단위 구조(salvage), 0 채움, 한도 초과 시 중단
- 검증 — 복제-중-해시 방식: 복제 후 원본이 드리프트해도 통과, 대상 손상은 탐지
- 취소 / 일시정지 / 재개, 진행률 0→100%
- GPT 보정 — 백업 헤더 이동, CRC32, LastUsableLBA, 보호 MBR, 데이터 영역 보존
- 읽기 가능 길이 탐색 — VSS 섀도 복사본의 크기 오보고 대응 (이진 탐색 경계 조건)
- CRC-32 표준 검증 벡터

**아직 검증되지 않음 / 범위 밖:**

- **다른 하드웨어(다른 PC)로 이식 후 부팅** — 클론을 원본과 다른 PC에 꽂으면 `0x0000007B
  (INACCESSIBLE_BOOT_DEVICE)` 파란 화면이 날 수 있습니다. 이는 클론 결함이 아니라 Windows의
  하드웨어 이식 문제로(원본 디스크를 그대로 옮겨도 동일), 새 PC BIOS의 저장소 모드를
  AHCI로 바꾸거나 Windows 시작 복구로 해결합니다. 이 도구의 역할(정확한 복제)과는 별개입니다.
- **대용량 디스크에서의 장시간 동작** — 실기 클론은 약 216GB였습니다. 더 큰 규모는 시간이 더 걸립니다.

여전히 **v0.x 시험판**입니다. 되돌릴 수 없는 작업이므로, 반드시 중요한 데이터를 먼저 백업하십시오.

### 테스트 실행

```powershell
dotnet build DiskMigrator.slnx -c Release

# 1) 읽기 전용 하드웨어 진단 — 디스크 열거와 SafetyGuard 판정 확인
dotnet run --project tools/DiskMigrator.Probe

# 2) 쓰기 없이 계획만 검증 — 실제 클론 전에 반드시 통과해야 하는 관문.
#    VSS 스냅샷 생성, 구간 조립, 스냅샷 읽기를 몇 초 만에 확인합니다.
#    관리자 권한 필요. 어떤 디스크에도 쓰지 않습니다.
.\tools\DiskMigrator.VhdTest\bin\Release\net8.0-windows\DiskMigrator.VhdTest.exe 0 --plan-only --snapshot

# 3) VHD 대상 end-to-end 클론 — 임시 VHD만 다루며 물리 디스크는 건드리지 않습니다.
.\tools\vhd-clone-test.ps1              # 오프라인 클론
.\tools\vhd-clone-test.ps1 -UseSnapshot # VSS 핫 클론
```

`DiskMigrator.VhdTest`의 클론 모드는 버스 종류가 `FileBackedVirtual`이 아니면 쓰기를 거부합니다 —
검증하려는 대상이 SafetyGuard 자신이므로, 그것과 무관한 방어선을 한 겹 더 둔 것입니다.
`--plan-only`는 대상을 열지 않으므로 이 제한을 받지 않습니다.

## 기여와 테스트

실제 디스크에 쓰는 테스트는 **반드시 버려도 되는 USB/HDD 또는 가상머신**에서 하십시오. 개발 중에는 `FileBlockDevice`나 `FaultyBlockDevice`로 충분히 검증할 수 있습니다.

원시 디스크 접근 도구는 백신이 의심할 수 있습니다. 코드를 공개하는 이유 중 하나입니다.
